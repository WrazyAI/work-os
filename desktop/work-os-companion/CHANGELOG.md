# Work OS Companion changelog


An employee reads this right after installing an update, so every entry is
one short, plain bullet: what changed for them, in their words. No jargon,
no file names, no implementation detail. One bullet per change, one line per
bullet, each under ~160 characters.

- Lead with the outcome: `Downloads now resume after a failed update.`
- Name the action the employee takes, not the system that changed.
- Longer notes are only for a complex change that cannot be understood in
  one line — a new workflow with steps or a behavior change with conditions.
  Even then, lead with the one-line version first.

Every release adds one `## <canonical-version> — <YYYY-MM-DD>` section below,
where the date is the day the build shipped; the What's New history shows it
next to the version. Versions stay in canonical SemVer here (`0.3.9`, never
the padded display form `0.3.09`); the UI pads the patch segment for display.
**Updating this file is a hard release requirement: the release workflow fails
when the released version has no matching section with at least one bullet**,
and the GitHub release notes are built from that section. While work is in
flight, collect entries under `## Unreleased`; when cutting a release, move
them under the new `## <version> — <ship-date>` heading. Omit refactors,
chores, and internal tooling unless they change what the employee sees or does.
